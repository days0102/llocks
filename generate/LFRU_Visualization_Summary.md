# LFRU 算法可视化与对比总结

## 一、算法工作流程可视化

### 1.1 锁的生命周期

```
┌─────────────────────────────────────────────────────────────┐
│                        锁的完整生命周期                        │
└─────────────────────────────────────────────────────────────┘

    ① 锁被创建
    │
    ↓
    ┌──────────────────────────────────────────┐
    │ ldlm_lfru_add_lock(ns, lock)             │
    │                                          │
    │  score = 0 + 1 = 1                      │
    │  阈值 = 1 (初始)                         │
    │  score > 阈值? NO                        │
    └──────────────────────────────────────────┘
    │
    ├─→ 普通列表
    │   │
    │   ├─ 再被访问
    │   │  └─ score = 2
    │   │     score > 阈值? 取决于阈值
    │   │
    │   └─ 缓存满
    │      └─ 优先驱逐 ✓ (LRU: 最旧)
    │
    └─→ 特权列表 (假设score足够高)
        │
        ├─ 一旦晋升，保持到驱逐 (不会被降级)
        │
        ├─ 再被访问
        │  └─ score++ (继续增加)
        │
        └─ 批量降级 (仅当列表超限)
           ├─ score >>= 2 (除以4)
           ├─ 回到普通列表
           └─ 重新竞争
           
    ② 缓存驱逐时
    │
    ↓
    ┌──────────────────────────────────────────┐
    │ ldlm_lfru_remove_lock(ns, lock)          │
    │                                          │
    │  驱逐顺序:                                │
    │  1. 优先驱逐普通列表 (最旧的)             │
    │  2. 普通列表空 → 驱逐特权列表             │
    └──────────────────────────────────────────┘
```

### 1.2 缓存状态演变（实时示例）

```
时刻 0：初始化
┌─────────────────────────────────┐
│  特权列表      普通列表          │
│  (0个)        (0个)             │
│                                 │
│  阈值 = 1                        │
└─────────────────────────────────┘

时刻 1：访问 Lock-A (score=1)
┌─────────────────────────────────┐
│  特权列表      普通列表          │
│  (0个)        Lock-A(1) ← 新    │
│                                 │
│  阈值 = 1                        │
│  原因: score=1 不大于阈值        │
└─────────────────────────────────┘

时刻 2：访问 Lock-A 再次 (score=2)
┌─────────────────────────────────┐
│  特权列表      普通列表          │
│  Lock-A(2)    (0个) ← 被提升   │
│                                 │
│  阈值 = 2 ↑                      │
│  原因: score=2 > threshold=1    │
│       晋升并更新阈值            │
└─────────────────────────────────┘

时刻 3：扫描 Lock-B, C, D... (各score=1)
┌─────────────────────────────────┐
│  特权列表      普通列表          │
│  Lock-A(2)    Lock-B(1)        │
│              Lock-C(1)         │
│              Lock-D(1)         │
│              ...                │
│                                 │
│  阈值 = 2                        │
│  原因: 扫描锁的score都是1       │
│       不超过新阈值2             │
│  结果: 扫描未污染缓存!✓         │
└─────────────────────────────────┘

时刻 4：再访问 Lock-E (score=3)
┌─────────────────────────────────┐
│  特权列表      普通列表          │
│  Lock-A(2)    Lock-B(1)        │
│  Lock-E(3)    Lock-C(1)        │
│               Lock-D(1)        │
│               ...                │
│  阈值 = 3 ↑↑                     │
│  原因: score=3 > threshold=2    │
└─────────────────────────────────┘
```

## 二、四种关键操作的流程图

### 2.1 ldlm_lfru_add_lock 流程

```
输入: namespace, lock
      [初始 lock->l_lru_score = N]

    ↓
┌────────────────────────────────┐
│ ns->ns_nr_unused++             │  计数+1
└────────────────────────────────┘
    ↓
┌────────────────────────────────┐
│ lock->l_lru_score++            │  评分+1
│ (限制在254以内)                │
└────────────────────────────────┘
    ↓
┌────────────────────────────────┐
│ new_priv = score > threshold?  │  判断是否晋升
└────────────────────────────────┘
    ↓
    ├─ YES (score > threshold 或 score == 254)
    │   │
    │   ├─ list_add_tail(priv_list)
    │   ├─ ns->ns_nr_priv++
    │   ├─ lock->l_lru_type = LRU_PRIV
    │   └─ ldlm_check_and_adjust_lfru_thresh()
    │       ├─ 如果 score > 当前threshold
    │       │  → threshold = score
    │       │  → access_cnt = 0 (重置)
    │       └─ 否则处理窗口逻辑
    │
    └─ NO (score ≤ threshold)
        │
        ├─ list_add_tail(normal_list)
        ├─ lock->l_lru_type = LRU_NORMAL_LIST
        └─ (仅当锁从未晋升过时调用adjust)

输出: 锁已添加到相应列表
```

### 2.2 ldlm_check_and_adjust_lfru_thresh 流程

```
输入: namespace, score
      [当前 threshold, max_freq, access_cnt, window_size]

    ↓
┌────────────────────────────────────────────┐
│ 条件1: score > threshold OR                │
│        score == PRIV_THRESH_CAP (254)?    │
└────────────────────────────────────────────┘
    ├─ YES
    │   ├─ threshold = score (立即提升)
    │   ├─ max_freq = 1 (重置)
    │   ├─ access_cnt = 0 (重置)
    │   └─ return (直接返回，不继续)
    │
    └─ NO → 继续
        ↓
    ┌────────────────────────────────────────────┐
    │ score > max_freq? 更新max_freq             │
    │ access_cnt++ (窗口计数+1)                  │
    └────────────────────────────────────────────┘
        ↓
    ┌────────────────────────────────────────────┐
    │ 条件2: access_cnt == window_size?         │
    │        (窗口满)                            │
    └────────────────────────────────────────────┘
        ├─ YES
        │   ├─ threshold = max_freq (基于本周期最高分)
        │   ├─ max_freq = 1 (重置)
        │   ├─ access_cnt = 0 (重置)
        │   └─ return
        │
        └─ NO → 检查条件3
            ↓
        ┌────────────────────────────────────────────┐
        │ 条件3: access_cnt == window_size / 2?     │
        │        (窗口半满)                          │
        └────────────────────────────────────────────┘
            └─ YES
                └─ max_freq = max_freq * 3 / 4
                   (衰减旧的访问模式 75%)

输出: 阈值可能被更新，反映当前工作负载
```

### 2.3 ldlm_lfru_try_batch_demote_locks 流程

```
输入: namespace, batch_size (通常=10)

    ↓
┌────────────────────────────────────┐
│ 特权列表为空?                       │
└────────────────────────────────────┘
    ├─ YES → return 0 (没有锁可降级)
    │
    └─ NO → 继续
        ↓
    ┌────────────────────────────────────────────────┐
    │ batch_size == PRIV_PER_ROUND_LIMIT (10) &&    │
    │ !priv_too_many()?                            │
    │ (正常流量且列表未超限)                         │
    └────────────────────────────────────────────────┘
        ├─ YES → return 0 (暂不降级，保护特权)
        │
        └─ NO → 继续降级
            ↓
        ┌────────────────────────────────────────────────┐
        │ 遍历特权列表 (从最旧的开始)                     │
        │ for each lock in priv_list:                   │
        └────────────────────────────────────────────────┘
            ↓
        ┌────────────────────────────────────────────────┐
        │ evicts < batch_size? (还未达到批次上限)        │
        └────────────────────────────────────────────────┘
            ├─ YES
            │   ├─ ldlm_lfru_demote_lock(ns, lock)
            │   │   ├─ 从特权列表移除
            │   │   ├─ score >>= 2 (除以4)
            │   │   └─ 添加到普通列表
            │   ├─ evicts++
            │   └─ 继续下一个锁
            │
            └─ NO → break (停止降级)

输出: evicts (实际降级的锁数)
```

### 2.4 ldlm_lfru_demote_lock 流程

```
输入: namespace, lock
      [必须是 LRU_PRIV 状态的锁]

    ↓
┌────────────────────────────────┐
│ lock->l_flags & LDLM_FL_NS_SRV? │  服务器端锁?
└────────────────────────────────┘
    ├─ YES → return (不处理)
    │
    └─ NO → 继续
        ↓
    ┌────────────────────────────────┐
    │ ldlm_lfru_remove_lock()        │  从特权列表移除
    │ (包括 ns->ns_nr_priv--)        │
    └────────────────────────────────┘
        ↓
    ┌────────────────────────────────┐
    │ ns->ns_nr_unused++             │  重新计数
    └────────────────────────────────┘
        ↓
    ┌────────────────────────────────┐
    │ list_add_tail(normal_list)     │  添加到普通列表
    │ lock->l_lru_type = NORMAL      │
    └────────────────────────────────┘
        ↓
    ┌────────────────────────────────┐
    │ lock->l_lru_score >>= 2        │  削减评分 (÷4)
    │ 例: 8 → 2, 4 → 1              │
    └────────────────────────────────┘

输出: 锁已从特权列表降级回普通列表，评分削减
```

## 三、关键参数和常数表

### 3.1 命名空间中的LFRU相关字段

```c
struct ldlm_namespace {
    // ===== 两个列表 =====
    struct list_head ns_unused_priv_list;     // 特权列表
    struct list_head ns_unused_normal_list;   // 普通列表
    
    // ===== 计数 =====
    unsigned int ns_nr_unused;    // 总未使用锁数 (priv + normal)
    unsigned int ns_nr_priv;      // 特权列表中的锁数
    
    // ===== 阈值相关 =====
    __u8 ns_lfru_priv_score_threshold;  // 当前晋升阈值 (0-254)
    
    // ===== 时间窗口机制 =====
    unsigned int ns_lfru_access_window_cnt;   // 当前窗口中的访问计数
    unsigned int ns_lfru_check_window_size;   // 窗口大小 (通常=max_unused/10)
    __u8 ns_lfru_max_freq;                    // 窗口内的最高评分
    
    // ===== 限制参数 =====
    __s8 ns_lfru_priv_ratio_limit_256;  // 特权列表比例限制 (分母256)
};
```

### 3.2 常数定义

```c
LDLM_LFRU_MIN_PRIV_THRESH       = 1      // 最低阈值
LDLM_LFRU_PRIV_THRESH_CAP       = 254    // 评分上限
LDLM_LFRU_PRIV_LIST_RATIO_LIMIT = 30     // 30% 比例限制
LDLM_LFRU_PRIV_PER_ROUND_LIMIT  = 10     // 每轮最多降级10个
LDLM_LFRU_UPDATE_WINDOW_DIV     = 10     // 窗口 = LRU_SIZE / 10
```

### 3.3 锁中的LFRU相关字段

```c
struct ldlm_lock {
    u8 l_lru_score;                    // 访问评分 (0-254)
    enum lru_list_type l_lru_type: 1;  // 所属列表 (LRU_NORMAL 或 LRU_PRIV)
    struct list_head l_lru;            // 链表节点 (用于两个列表)
};
```

### 4.2 缓存污染对比

```
场景: 执行 ls -lR 遍历一个有100个文件的目录
(假设缓存容量也恰好是100)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LRU 的行为:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 访问 Lock-1 → 添加到LRU
2. 访问 Lock-2 → 添加到LRU
   ...
100. 访问 Lock-100 → 添加到LRU
   
结果: 缓存满
     100个目录项都被缓存
     之前的热点锁被驱逐 ✗ 缓存污染

再访问原来的热点 Lock-A:
     不在缓存中 → MISS ✗
     性能下降

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LFRU 的行为:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. 初始 threshold = 1

2. 访问 Lock-1: score=1 (=threshold) → 普通列表
3. 访问 Lock-2: score=1 → 普通列表
   ...
   阈值仍=1

3. 访问某个 Lock-H: score=2 > threshold(1)
   → 晋升到特权列表 ✓
   → 更新 threshold = 2
   
4. 之后访问 Lock-I...Z: score=1
   → 不超过新阈值 → 普通列表

结果: 特权列表: 1-2个锁 (真正的热点)
     普通列表: 98-99个锁 (扫描目录项)
     
再访问原来的热点:
     在特权列表 → HIT ✓
     性能保持

扫描操作对热点的影响: 最小化 ✓

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
对比总结:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
             被污染的锁数  缓存利用率    性能稳定性
LRU:         ~100 (100%)   低           ✗ 不稳定
LFRU:        ~0   (0%)     高           ✓ 稳定
```

## 五、初始化示例

```c
// 假设在命名空间初始化时调用

void init_lfru_cache(struct ldlm_namespace *ns, int max_unused)
{
    // 初始化列表
    INIT_LIST_HEAD(&ns->ns_unused_priv_list);
    INIT_LIST_HEAD(&ns->ns_unused_normal_list);
    
    // 初始化计数
    ns->ns_nr_unused = 0;
    ns->ns_nr_priv = 0;
    
    // 初始化阈值
    ns->ns_lfru_priv_score_threshold = LDLM_LFRU_MIN_PRIV_THRESH;  // 1
    ns->ns_lfru_max_freq = LDLM_LFRU_MIN_PRIV_THRESH;              // 1
    
    // 初始化窗口机制
    ns->ns_lfru_access_window_cnt = 0;
    ns->ns_lfru_check_window_size = max(max_unused / LDLM_LFRU_UPDATE_WINDOW_DIV, 1);
                                        // 通常 = LRU_SIZE / 10
    
    // 初始化比例限制 (30% 转换为分母256的形式)
    ns->ns_lfru_priv_ratio_limit_256 = (LDLM_LFRU_PRIV_LIST_RATIO_LIMIT << 8) / 100;
                                        // 30 * 256 / 100 = 77
    
    // 绑定操作回调
    ns->ns_lock_cache_ops = &ldlm_lfru_cache_ops;
}
```

## 六、性能分析

### 6.1 时间复杂度

| 操作 | 复杂度 | 说明 |
|------|--------|------|
| 添加锁 | O(1) | 链表尾插 + 阈值调整都是常数 |
| 移除锁 | O(1) | 链表删除 |
| 批量降级 | O(B) | B=batch_size，通常10 |
| 每次驱逐 | O(1) | 链表头删除 |
| 整体插入-删除周期 | O(N) | N=缓存大小，但均摊O(1) |

### 6.2 空间复杂度

```
每把锁:
  l_lru_score: 1字节 (0-254)
  l_lru_type:  1位 (LRU_NORMAL 或 LRU_PRIV)
  l_lru:       双向链表指针 (已存在，复用)
  
命名空间:
  ns_nr_priv: 4字节
  ns_lfru_priv_score_threshold: 1字节
  ns_lfru_max_freq: 1字节
  ns_lfru_access_window_cnt: 4字节
  ns_lfru_check_window_size: 4字节
  ns_lfru_priv_ratio_limit_256: 1字节
  
总开销: ~ 1字节/锁 + 常数命名空间开销
相比LRU: +1字节/锁 (非常节省)
```

### 6.3 缓存命中率改进

基于论文 (https://arxiv.org/abs/1702.04078) 的数据:

```
工作负载 1: 热点集中 (帕累托分布)
  LRU:  75% 命中率
  LFRU: 89% 命中率
  改进: +18.7%

工作负载 2: 随机访问
  LRU:  60% 命中率
  LFRU: 62% 命中率
  改进: +3.3%

工作负载 3: 频繁扫描 + 热点
  LRU:  45% 命中率
  LFRU: 78% 命中率
  改进: +73.3% ✓ (最明显的改进)

平均: 改进约 20-30%
```

## 七、实战应用指南

### 7.1 何时使用 LFRU

✓ 使用 LFRU 的场景:
```
1. 文件系统服务器 (Lustre, NFS)
   - 混合热点和冷门文件访问
   - 频繁的目录遍历和大扫描
   
2. 数据库锁管理
   - 热点行/页面的频繁访问
   - 偶发的全表扫描
   
3. 缓存大小有限的系统
   - 每字节缓存都很宝贵
   - 需要最大化命中率
   
4. 工作负载多变的系统
   - 访问模式随时间变化
   - 需要自适应的参数调整
```

✗ 不需要 LFRU 的场景:
```
1. 完全随机访问
   - LRU 已经足够
   
2. 纯粹的最近性重要
   - 例: 编译中间文件缓存
   
3. 访问模式完全确定
   - 可以手工优化 LRU
```

### 7.2 参数调优

```c
// 窗口大小调优
if (工作负载变化频繁) {
    check_window_size = LRU_SIZE / 5;  // 缩小窗口，快速响应
} else {
    check_window_size = LRU_SIZE / 20; // 放大窗口，稳定阈值
}

// 特权列表比例调优
if (热点集中) {
    priv_ratio = 10;  // 特权列表小，保护更少但更优的锁
} else {
    priv_ratio = 50;  // 特权列表大，保护更多锁
}

// 衰减因子调优
if (工作负载变化快) {
    decay_factor = 0.5;  // 更激进的衰减 (当前: 0.75)
} else {
    decay_factor = 0.9;  // 更保守的衰减
}
```

## 八、常见问题解答

### Q1: 为什么评分用 u8 (0-254) 而不是更大的类型?

A: 
```
1. 空间效率: 每把锁节省7字节
2. 评分饱和: 10次访问就达到10，200多次达到上限
3. 衰减设计: 降级时 >>2 防止溢出
4. 评分含义: 不需要精确计数，只需相对大小关系
```

### Q2: 为什么晋升不可逆（一旦晋升不再降级）?

A:
```
1. 简化逻辑: 避免频繁的升降
2. 保护热点: 确保识别出的热点锁不被污染
3. 公平性: 只在列表超限时才强制降级
4. 稳定性: 减少缓存中的"翻滚"
```

### Q3: 为什么需要 ns_lfru_max_freq（最大频率）?

A:
```
1. 适应工作负载变化
2. 实现自动衰减机制
3. 反映"当前"而非"历史"的工作特征
4. 避免阈值被太陈旧的数据锁定
```

### Q4: 为什么降级因子选择 0.75 (3/4)?

A:
```
1. 实验经验值（论文中推荐）
2. 保留 25% 信息（不完全遗忘）
3. 位运算实现: *3/4 比 *0.75 快
4. 平衡快速适应和稳定性
```

### Q5: 如何诊断 LFRU 参数不当?

A:
```
症状                    原因                    方案
─────────────────────────────────────────────────────────
特权列表过小(< 1%)     窗口太大               缩小 window_size
                       阈值提升过快

特权列表过大(> 50%)    窗口太小               放大 window_size
                       衰减因子太大          或调大衰减

扫描后缓存Hit低         阈值调整慢             缩小窗口
                       衰减不足

性能不稳定            窗口太小，抖动          放大窗口
                      阈值频繁变化           平滑变化
```

## 总结

LFRU 算法通过以下设计优雅地解决了缓存污染问题：

1. **分层保护** - 特权列表优先级高，普通列表优先驱逐
2. **自适应阈值** - 通过时间窗口自动调整晋升标准
3. **扫描抵抗** - 快速提升阈值隔离一次性大访问
4. **内存高效** - 仅增加1字节/锁，复用现有链表
5. **实现简单** - 核心逻辑仅几百行代码

相比 LRU，在混合工作负载下可以提高 20-73% 的缓存命中率。
